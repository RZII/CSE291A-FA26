本文档整理 Phase 1 在 AWS GPU 实例上做的全部实验：实验设置、复现方法、原始数据位置、主要结果和分析。

共三部分实验，全部在同一台机器、同一个模型和运行时上完成：

| 部分 | 内容 | 矩阵 | 运行数 | 数据 |
|---|---|---|---|---|
| 一 | 基线负载（GSM8K + HotpotQA 短任务）：A–I 组 + GPU/CPU 放置 T1–T3 组 | `experiments/gpu.toml` | 129（43 个条件 × 3） | `phase1/data/gpu/` |
| 二 | 搬运 vs 重算微基准 | `scripts/bench_transfer.py` | 54（3 种放置 × 6 种长度 × 3） | `phase1/data/bench_transfer/` |
| 三 | 长上下文补充实验（逐页阅读长文档） | `experiments/longctx.toml` | 39（13 个条件 × 3） | `phase1/data/longctx/` |

图在 `phase1/figs/`，按条件汇总的表在 `phase1/tables/`。文件说明见 `phase1/README.md`。

## 1 实验设置

### 1.1 硬件与软件

- 实例：AWS g6.2xlarge（us-west-2），NVIDIA L4 24 GB 显存（可用 23 GB），8 vCPU，32 GB 主机内存，显存与主机内存之间走 PCIe。
- 系统：Deep Learning Base AMI with Single CUDA（Ubuntu 24.04）。
- 运行时：llama.cpp build 11669（commit 620d2225c），CUDA 编译（`-DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=native`）。
- 模型：Qwen3-4B-Instruct-2507，Q8_0 量化（约 4.3 GB），所有实验不变；解码 temperature 0。
- 环境安装：`bash scripts/aws_setup.sh`（编译 llama.cpp、安装 uv 和依赖、预下载模型）。

### 1.2 服务器与调度器

llama-server 启动参数：`-c <ctx> -np <slots> -kvu --cache-ram <MiB> -ngl <层数> [--no-kv-offload] --fit off -lv 4`。

- **KV 预算（ctx）**：所有槽共享一个容量为 ctx 个 token 的 KV 池（`-kvu`），启动时一次性分配。该模型每个 token 的 KV
  占 144 KiB，32K token ≈ 4.5 GiB，16K token 的一段上下文 = 2304 MiB。
- **主机缓存（cache_ram）**：槽里被替换出去的上下文存到主机内存，同一请求序列回来时从主机内存搬回显存，不用重算。
- **放置**：`-ngl` 决定多少层权重放显存（99 = 全部 36 层），`--no-kv-offload` 把整个 KV 池放到主机内存。
- `--fit off` 保证不会自动缩小参数；`-lv 4` 让日志记录每次主机缓存的存取及耗时，`scripts/cache_transfers.py` 从中解析出搬运量和带宽。

调度器是 agent 和服务器之间的 HTTP 代理，单个 FIFO 队列，最多同时转发 K 个请求（这就是本阶段的基线策略：FIFO + 固定并发 K）。
队列足够大，不会拒绝请求，观察到的失败都来自模型端。

### 1.3 负载

- **基线负载（第一、二部分）**：GSM8K 测试集 10 题（Python 工具）+ HotpotQA dev-distractor 10 题（BM25 检索），每次运行 20 个任务、顺序打乱，
  由 N 个闭环 agent 执行，每次工具调用后额外等待固定的工具延迟。单个任务的上下文通常在 300–2000 token。
- **长上下文负载（第三部分）**：LongBench 中的长文档问答（`data/longqa_50.jsonl`，由 `scripts/build_tasks.py longqa` 生成，取前 20 题）。
  每篇文档约 1 万词，切成 9–16 页，agent 用 `read_page` 工具一页一页地读，最后给出答案（用 HotpotQA 的方式评分）。
  每读一页上下文增加约 1.4K token：任务结束时的上下文 p10 / p50 / p90 / 最大 = 1.6K / 5.3K / 17.9K / 18.1K token，步数中位数 4.5、最多 16。
  文档段落经过固定种子打乱，避免答案总在第一页。

### 1.4 指标

由 `scripts/analyze.py` 从事件日志、调度器日志、llama.log 和 `gpu.jsonl`（`scripts/sample_gpu.py` 采样 nvidia-smi）计算：

| 指标 | 含义 |
|---|---|
| accuracy / failure_rate | 答对比例 / 未能给出答案的比例（KV 溢出、超时等） |
| throughput | 答出的任务数 / 运行总时长（任务/分钟）。注意失败的任务会提前结束，可能让总时长变短 |
| completion p50 / p95 | 单个任务从开始到结束的时间 |
| queue p95 | 请求在调度器队列中等待的时间 |
| kv_full_events | llama.log 中 "failed to find free space in the KV cache" 的次数，即 KV 池满的精确信号 |
| context_overflow | 生成过程中上下文超出可用空间，服务器返回 500 "Context size has been exceeded" |
| cached_frac / recompute_tokens | 请求的 prompt 中命中缓存的比例 / 需要重新计算的前缀 token 数 |
| vram_peak_mb / gpu_util | 显存峰值 / GPU 平均利用率（nvidia-smi） |
| cache_saves / loads | 主机缓存的存、取次数及耗时 |
| deadline_miss_60s / 120s | 60 s / 120 s 内没有答出的任务比例 |

### 1.5 复现

```

uv run --group analysis python -m scripts.bench_transfer --out logs/bench_transfer --placements gpu kv_cpu layers18 --llama-cmd ~/llama.cpp/build/bin/llama-server
```

`conditions.csv` 是按条件（3 次重复取平均，`_std` 列为标准差）汇总的表。

## 2 基线负载的结果（第一部分）

基线条件：K=2、4 个 agent、32K KV 预算、4 个槽、8 GB 主机缓存、全部放显存、工具延迟 3 s、检索返回 5 段、短回复。
每组只改一个因素（H 组改两个）。基线负载下准确率基本固定在 0.85（temperature 0，同样的题），下面主要看性能和失败。

### 2.1 并发（A 组：K × agent 数）

| K \ agent | 2 | 4 | 8 |
|---|---|---|---|
| 1 | 21.0 | 29.5 | 32.9 |
| 2 | 21.8 | 34.5 | 47.0 |
| 4 | 21.8 | 37.2 | **55.2** |

（吞吐量，任务/分钟）

- agent 少时 K 不起作用：2 个 agent 时 K=1/2/4 的吞吐量都约 21，瓶颈在 agent 自己（工具等待）。
- 8 个 agent 时 K 从 1 到 4 吞吐量提高 68%（32.9 → 55.2），完成时间 p50 从 12.7 s 降到 6.6 s，队列等待 p95 从 6.1 s 降到 1.0 s。
- GPU 利用率：K=1、8 agent 时 92%，但吞吐量最低——GPU 忙于一次处理一个请求；K=4 时 68%，吞吐量最高，说明批处理效率更好。
- 32K 预算下 KV 峰值只用了约 3.9K token，没有任何失败，显存峰值固定在 9.0 GB（模型 + 4.5 GiB 的 KV 池）。

### 2.2 KV 预算（B 组，K=4，8 agent）

| ctx | 4K | 8K | 16K | 32K |
|---|---|---|---|---|
| 吞吐量 | 56.5 | 55.0 | 56.1 | 55.2 |
| 显存峰值 (GB) | 4.96 | 5.54 | 6.70 | 9.02 |
| 失败率 | 0 | 0 | 0 | 0 |

短任务下 KV 峰值约 4K token，所以 4K 预算就够用，再大只是多占显存（KV 池启动时就全部分配，大小 = ctx × 144 KiB）。
**这说明基线负载对 KV 的需求太小，预算不是瓶颈**，这也是后面加长回复和长上下文实验的原因。

### 2.3 上下文长度（C 组：检索段数 2 / 5 / 10 / 20）

检索段数从 2 增到 20，KV 峰值从 1.25K 涨到 7.8K token，命中缓存的比例从 0.57 降到 0.17，吞吐量从 36.2 降到 30.9，完成时间 p50 从 5.5 s 增到 6.9 s。
准确率在 0.83–0.88 之间，没有明显变化。上下文变长主要增加 prefill 量，32K 预算下不会失败。

### 2.4 工具延迟 / 步骤间空闲（D 组：0 / 1 / 3 / 10 s）

| 延迟 | 0 s | 1 s | 3 s | 10 s |
|---|---|---|---|---|
| 吞吐量 | 53.4 | 50.6 | 34.5 | 16.0 |
| 完成时间 p50 (s) | 4.2 | 4.4 | 5.7 | 12.2 |
| GPU 利用率 | 82% | 81% | 71% | 33% |

短任务下工具等待时间占了任务的大部分。10 s 延迟时 GPU 有三分之二的时间是空的，但这些空闲 agent 的 KV 仍然占着池子。

### 2.5 上下文保留（E 组：默认 / 关主机缓存 / 关前缀复用）

吞吐量 34.5 / 36.4 / 35.0，完成时间 p50 5.7 / 5.4 / 5.9 s，三者差别在误差范围内。
原因：短上下文在 L4 上重算一次只要几百毫秒（见第 3 节），省下的时间很少；而主机缓存本身的存取也有开销。
**短任务下，保留上下文几乎没有收益**，这一点在长上下文下完全反过来（第 4 节）。

### 2.6 回复长度（F 组：短 / 长 / 混合，32K 预算）

| 回复 | 短 | 混合 | 长 |
|---|---|---|---|
| 吞吐量 | 34.5 | 15.1 | 8.8 |
| 输出 token p95 | 81 | 484 | 537 |
| 完成时间 p95 (s) | 9.8 | 26.7 | 40.2 |
| GPU 利用率 | 71% | 85% | 89% |

混合负载中，短任务的完成时间 p95 从 9.8 s 涨到 15.9 s：短任务排在长回复后面等待（FIFO 的队头阻塞）。32K 预算下依然没有失败。

### 2.7 小预算下的长回复和并发（G、H 组）

把预算降到 4K–8K（每个 agent 能分到的 KV 接近单个任务的需求），长回复开始撑爆 KV 池：

| 条件（8 agent，混合回复） | 4K | 6K | 8K |
|---|---|---|---|
| K=1 失败率 / 吞吐量 | 0 / 9.5 | 0 / 9.4 | 0 / 9.5 |
| K=2 失败率 / 吞吐量 | 3% / 16.4 | 0 / 15.5 | 0 / 15.9 |
| K=4 失败率 / 吞吐量 | **53%** / 16.0 | 7% / 20.2 | 0 / 23.3 |

- G 组：K=4、4K 预算、全部长回复时失败率 73%，准确率掉到 0.23，平均每次运行 147 次 KV 池满。
- 所有失败都是 context_overflow（生成过程中 KV 池被占满），不是超时。
- 小预算下没有一个 K 同时做到最好：K=1 不失败但吞吐量只有 9.5、60 s 截止未达率 22%；K=4 吞吐量最高，但在 4K 时一半任务失败。
  **合适的并发度取决于当前 KV 的余量**，而固定 K 的 FIFO 看不到这一点。

### 2.8 小预算下的空闲时间（I 组：K=4，6K 预算，混合回复）

工具延迟 0 / 3 / 10 s：失败率都是 7%，吞吐量 23.2 / 20.2 / 17.2，KV 池满次数 11 / 10.7 / 7。
在这个规模下，空闲时间的长短对失败影响不大。

### 2.9 GPU / CPU 放置（T1–T3 组，K=4，8 agent）

**T1：KV 池放显存还是主机内存**

| | KV 在显存 | KV 在主机内存 |
|---|---|---|
| 32K 预算：显存峰值 | 9.02 GB | 4.51 GB |
| 32K 预算：吞吐量 | 55.2 | 33.9（−39%） |
| 32K 预算：完成时间 p50 | 6.6 s | 10.9 s |
| 8K 预算：显存峰值 / 吞吐量 | 5.54 GB / 55.0 | 4.39 GB / 33.1 |

整个 KV 池放到主机内存能省一半显存，但每一步注意力计算都要读主机内存，吞吐量下降约四成。

**T2：部分层放 CPU（`-ngl`）**

| 显存中的层数 | 全部 (99) | 32 | 27 | 18 |
|---|---|---|---|---|
| 显存峰值 | 9.02 GB | 7.96 GB | 6.82 GB | 4.76 GB |
| 吞吐量 | 55.2 | 37.2（67%） | 27.7（50%） | 18.2（33%） |
| prefill ms/token | 0.37 | 0.59 | 0.87 | 1.36 |

每少放一些层，吞吐量大致按比例下降，CPU 计算成为瓶颈，GPU 利用率从 68% 降到 25%。
**静态地把权重或整个 KV 池挪到 CPU 都很贵**；如果要用主机内存，应当只放暂时不用的 KV（见第 3、4 节）。

**T3：主机缓存 × 工具延迟（8K 预算，混合回复）**

| | 有主机缓存 | 无主机缓存 |
|---|---|---|
| 延迟 0 s 吞吐量 | 23.6 | 26.5 |
| 延迟 10 s 吞吐量 | 17.5 | 18.4 |

短任务下主机缓存不但没用，还略有负面影响（存缓存的开销大于重算的节省），与 E 组一致。

## 3 搬运 vs 重算（第二部分）

单槽、无并发，测一段上下文 (a) 从头 prefill，(b) 存到主机缓存，(c) 从主机缓存取回所需的时间（3 次的中位数，ms）：

| 上下文 token | KV 大小 | 重算 (prefill) | 存到主机 | 从主机取回 | 存+取 / 重算 |
|---|---|---|---|---|---|
| 512 | 72 MiB | 96 | 42 | 15 | 0.59 |
| 2048 | 288 MiB | 422 | 155 | 47 | 0.48 |
| 4096 | 576 MiB | 896 | 306 | 90 | 0.44 |
| 8192 | 1152 MiB | 2020 | 604 | 178 | 0.39 |
| 16384 | 2304 MiB | 5122 | 1202 | 352 | 0.30 |

（放置 = 全部在显存。存约 1.9 GB/s，取约 6.5 GB/s。图：`phase1/figs/transfer.png`）

- 在独立 GPU 上搬运不是免费的：存+取只比重算便宜 1.7–3.3 倍；但**只看取回**，16K 上下文取回 0.35 s，重算 5.1 s，相差 14 倍。
  存可以在 agent 等工具时做，不在关键路径上；真正影响延迟的是取回。
- 上下文越长，重算越贵（prefill 是超线性的：16K 的单 token 成本是 512 的 1.7 倍），搬运的优势越大。
- 上表是空载下的数字。在并发负载下重算会和其他请求抢 GPU，实际代价大得多（第 4 节中一次 17K 的重算用了 72 s）。
- KV 放主机内存（kv_cpu）或部分层放 CPU（layers18）时，搬运时间几乎不变，但重算更慢（16K：8.0 s / 11.6 s）。

## 4 长上下文补充实验（第三部分）

基线负载的上下文太短，KV 池永远不满、主机缓存也不起作用，无法反映"显存装不下所有 agent 的上下文"这种情况。
这部分用长文档阅读任务：16 个 agent、20 个任务，单个任务最长 18K token，所有 agent 的上下文加起来远超 KV 池。
预算选的是 L4 在放下模型之后实际能给 KV 的大小（98K token = 13.5 GiB，显存峰值 18.3 GB），不是为了制造压力而人为调小。

基线：K=4、65K 预算、8 个槽、8 GB 主机缓存、全部放显存、工具延迟 3 s、单任务上限 600 s、最多 16 步。

### 4.1 并发 × KV 预算（L1 组）

| | 32K | 65K | 98K |
|---|---|---|---|
| K=2 失败率 / 准确率 | 23% / 0.48 | 7% / 0.57 | **0** / 0.58 |
| K=4 失败率 / 准确率 | 37% / 0.42 | **32%** / 0.48 | **0** / 0.58 |
| K=8 失败率 / 准确率 | **72%** / 0.17 | 40% / 0.35 | 23% / 0.47 |

失败原因（3 次运行合计，每次 20 个任务）：

| | 32K | 65K | 98K |
|---|---|---|---|
| K=2 | 14 次溢出 | 4 次超时 | 无 |
| K=4 | 22 次溢出 | **19 次超时** | 无 |
| K=8 | 43 次溢出 | 24 次溢出 | 14 次溢出 |

- 32K 预算下 K 越大失败越多（23% → 37% → 72%），全部是 KV 池满，每次运行有 74–93 次池满事件。
  这与 2.7 节小预算下的现象相同，只是这里的预算是真实大小。
- 98K 预算下 K=2 和 K=4 都不失败，但 K=8 仍有 23% 溢出：8 个长上下文同时推进时能占到 94K token。
- 32K 下的吞吐量看起来最高（4.3 任务/分钟），是因为失败的任务提前结束，缩短了运行总时长，不代表更好。
- 显存峰值随预算变化：9.0 / 13.7 / 18.3 GB。

### 4.2 65K 预算下的超时：被挤出的上下文要重算

K=4、65K 时 KV 池从未满过，但失败率仍有 32%，全是超过 600 s 的超时。从 llama.log 统计每次运行中超过 8K token 的大段 prefill：

| K=4 | 32K | 65K | 98K |
|---|---|---|---|
| prefill 总量（token / 运行） | 13.8 万 | **26.1 万** | 17.5 万 |
| prefill 总耗时（s / 运行） | 122 | **507** | 267 |
| 超过 8K token 的 prefill 次数 | 1–2 | **7–9** | 0–2 |
| 这些大 prefill 的耗时（s） | 10–30 | **278–364** | 0–100 |
| 需要重算的前缀 token | 3.3 万 | 10.5 万 | 1.3 万 |

16 个 agent 的上下文加起来超过 65K，而同一时刻只有 4 个在推理。等工具的 agent 的 KV 留在槽里，会被正在推理的
agent 挤掉；8 GB 的主机缓存也装不下所有人。它们回来时要把 10K–17K token 的上下文从头 prefill，和其他请求挤在一起，
一次要 38–72 s，单个任务这样来几次就会超过 600 s。预算加到 98K，挤出几乎不再发生，prefill 总耗时减半，失败归零。
32K 下没有这个问题，是因为长任务在变长之前就已经溢出失败了。

这是本阶段最重要的观察：**KV 池不满并不等于没有内存压力**。被挤出的长上下文要么重算（这里一次几十秒），要么从主机内存
取回（第 3 节：16K 约 0.35 s）。默认的主机缓存是被动的、按 LRU 淘汰，容量有限，也不知道哪个 agent 什么时候回来。

### 4.3 上下文保留（L2 组：K=4，65K）

| | 默认 | 关主机缓存 | 关前缀复用 |
|---|---|---|---|
| 完成时间 p50 | **66 s** | 150 s | 138 s |
| 失败率 | 32% | 35% | 37% |
| 命中缓存比例 | 0.69 | 0.28 | 0 |
| 需要重算的前缀 token | 10.5 万 | 23.9 万 | 39.9 万 |
| 120 s 截止未达率 | 37% | 53% | 52% |

和短任务（2.5 节）正好相反：长上下文下关掉主机缓存，中位完成时间增加一倍多，重算量增加 1.3 倍。保留上下文在这里是必要的。

### 4.4 工具延迟（L3 组：0 / 3 / 10 s）

失败率 28% / 32% / 27%，完成时间 p50 69 / 66 / 69 s，吞吐量 1.44 / 1.33 / 1.46，几乎没有差别。
长上下文下时间主要花在 prefill 上，几秒的工具等待已经不是瓶颈，这也与短任务（2.4 节）相反。

## 5 瓶颈总结

1. **短任务（基线负载）**：瓶颈是工具等待和调度并发度。KV 需求约 4K token，远小于预算；主机缓存和前缀复用收益可以忽略。
   提高 K 是最有效的手段（8 agent 时 K=1 → 4 吞吐量 +68%）。
2. **KV 余量紧张时**（小预算 + 长回复，或长上下文）：固定 K 的 FIFO 要么并发太低（吞吐量低、截止未达），要么太高（KV 溢出，失败率 50–70%）。
   合适的 K 随 KV 余量变化，而 FIFO 看不到 KV 状态。
3. **长上下文、KV 预算刚好够时**：失败来自被挤出的上下文重算，而不是池满。重算一段 10K–17K 的上下文在负载下要几十秒，从主机内存取回只要几百毫秒。
4. **静态放置代价很高**：KV 整体放主机内存吞吐量 −39%，权重部分放 CPU 吞吐量降到 33–67%。主机内存适合放"暂时不用"的 KV，不适合放正在计算的部分。
5. **回复长度带来队头阻塞**：混合负载下短任务 p95 从 9.8 s 增到 15.9 s。

## 6 对 Phase 2 的意义

基线策略（FIFO + 固定 K）在第 2、4 点上表现最差。Phase 2 可以考虑的方向（以组内讨论为准）：

- **感知 KV 余量的准入**：根据池中剩余空间和每个请求预计会增长的 token 数决定放行，代替固定 K。
- **按空闲状态分层存放 KV**：agent 等工具时，根据上下文长度和预计的等待时间，决定它的 KV 留在显存、搬到主机内存还是直接丢弃重算；
  在工具返回前提前搬回。第 3 节的数据可以直接作为代价模型（存 ~1.9 GB/s、取 ~6.5 GB/s、prefill 每 token 0.3–0.6 ms 并随长度增长）。
  llama.cpp 提供了可用的控制接口：`/slots/<id>?action=save|restore|erase` 和请求中的 `id_slot`。
- **对比基线**：最佳固定 K 的 FIFO、llama.cpp 自带的主机缓存、"总是丢弃重算"。
- **负载**：长上下文任务是体现差异的关键；基线负载可以作为"不应变差"的对照。

## 7 局限

- 每个条件 3 次重复；长上下文部分 K=8、98K 等条件的方差较大（失败率标准差约 20 个百分点）。
- 所有实验都是闭环负载（N 个 agent 做完一个任务再领下一个），没有测按到达率变化的开环负载，Phase 2 需要补。
- 只用了一个模型（4B，Q8_0）和一种 GPU（L4）；更大的模型会让 KV 占比和搬运代价都发生变化。
- 长上下文部分的准确率不高（最好 0.58），一部分是 4B 模型本身阅读长文档的能力所限，与调度无关；比较时应主要看失败率和时间。
- 任务的输出长度和总步数在运行前是未知的，本阶段没有分析能否预测，这会影响 Phase 2 准入策略的设计。
